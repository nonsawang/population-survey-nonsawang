# ปรับสถานะประชากรให้ตรง HOSxP

สถานะการติดตั้ง: ต้องรัน SQL ใน Supabase ก่อนใช้การบันทึกแบบใหม่
ไฟล์ SQL นี้ไม่ใช่คำสั่งสำหรับฐาน HOSxP/MariaDB

## โครงสร้างใหม่

- `residency_type`: ประเภทอยู่อาศัย 0–4 ตาม `house_regist_type` ของ HOSxP
- `person_discharge_id`: 1 เสียชีวิต, 2 ย้าย, 3 สาบสูญ, 9 ยังไม่จำหน่าย
- `legacy_residency_type`: ค่า Type เดิมเพื่อทบทวนข้อมูล
- `status_model_version`: 1 สำหรับข้อมูลแบบใหม่; 0 หรือไม่มีคอลัมน์หมายถึงข้อมูลแบบเดิม

Type 0 ใหม่หมายถึงมาอาศัยในเขตแต่ไม่อยู่ตามทะเบียนบ้าน เช่น คนเร่ร่อน
Type 4 ใหม่หมายถึงบุคคลนอกเขต ไม่ใช่เสียชีวิต

## ขั้นตอนติดตั้ง

1. สำรองฐาน Supabase ตามวิธีของหน่วยงาน และหยุดการบันทึกชั่วคราว
2. ใน SQL Editor ของ Supabase โปรเจกต์ระบบสำรวจ รัน `20260907_population_status.sql`
3. ตรวจผลสรุปท้ายคำสั่ง และติดตั้งโค้ดชุดนี้ให้เสร็จในช่วงหยุดบันทึกเดียวกัน
4. ให้ผู้ใช้ปิดหน้าเก่าและเปิดใหม่ก่อนกลับมาบันทึก เพื่อไม่ให้โค้ดเก่าใช้ Type 0/4 เป็นสถานะต่อ
5. ทดลองข้อมูลในฐานทดสอบ: Type 0 + ยังไม่จำหน่าย, Type 4 + ยังไม่จำหน่าย และ Type 1 + เสียชีวิต ต้องแสดงคนละสถานะ

คำสั่งทำงานใน transaction และสร้าง `population_status_backup_20260907` เก็บค่าสถานะเดิม
ตารางสำรองเปิด RLS โดยไม่มี policy ให้ผู้ใช้ทั่วไปอ่านข้อมูล ต้องใช้ผู้ดูแลในการตรวจหรือกู้คืน
การรันซ้ำจะไม่แปลงข้อมูลที่เป็นเวอร์ชัน 1 แล้วและไม่เขียนทับ snapshot เดิม

## ข้อมูลเก่าที่ต้องตรวจ

- Type 0 เดิม: ใช้ทั้งจำหน่ายและนอกเขต จึงล้างประเภทอยู่อาศัยและปล่อยเหตุจำหน่ายว่าง เก็บค่าเดิมไว้ ไม่เดาว่าเป็นย้ายหรือสาบสูญ
- Type 4 เดิม: ตามปุ่มเสียชีวิตเดิม แปลงเป็น `person_discharge_id=1` แต่ไม่เดาประเภทอยู่อาศัยเดิม จึงปล่อย `residency_type` ว่าง
- Type 1–3 เดิม: คงประเภทอยู่อาศัยและตั้งสถานะยังไม่จำหน่าย
- ข้อมูลที่ยังไม่มี Type ยังคงว่าง ไม่เปลี่ยนเป็น Type 3 อัตโนมัติ

หน้าเปิดบ้านจะแสดงข้อความให้ตรวจข้อมูลที่ยังไม่ครบ หากยังไม่มีโครงสร้างใหม่จะอ่านข้อมูลเก่าได้ แต่ปิดการบันทึกสถานะใหม่และแจ้งให้รัน migration
ฟังก์ชัน `hosxpStatusPayload` จะไม่สร้างข้อมูลส่งออกถ้ายังไม่ระบุประเภทอยู่อาศัยหรือเหตุจำหน่ายครบ
ชุดนี้ยังไม่ได้เขียนข้อมูลลงฐาน HOSxP การส่งข้อมูลจริง รวมถึงวันเสียชีวิตและสถานะอื่นที่สัมพันธ์กัน ต้องผ่านงานเชื่อมต่อที่ตรวจสอบแยกต่างหาก

## กู้คืน

หาก migration ล้มเหลว transaction จะไม่ถูก commit ให้แก้สาเหตุแล้วรันใหม่
หากต้องย้อนกลับหลังเปิดใช้งาน ให้ผู้ดูแลเปรียบเทียบ snapshot กับข้อมูลปัจจุบันก่อน ไม่คืนค่าทั้งตารางทับงานที่เพิ่งบันทึก
