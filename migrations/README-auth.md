# ระบบยืนยันตัวตนและสิทธิ์ (10 กันยายน 2569)

## สิทธิ์ที่บังคับในฐานข้อมูล

| บทบาท | ประชากร | บัญชีผู้ใช้ | ตรวจส่ง HOSxP |
|---|---|---|---|
| ไม่เข้าสู่ระบบ | ไม่มีสิทธิ์ | ไม่มีสิทธิ์ | ไม่มีสิทธิ์ |
| อสม. (`vhv`) | อ่าน/เพิ่ม/แก้ไขเฉพาะหมู่ใน `app_users.moo` | อ่านข้อมูลบัญชีตนเองที่ไม่ใช่รหัสผ่าน | ไม่มีสิทธิ์ |
| เจ้าหน้าที่ (`staff`) | อ่าน/เพิ่ม/แก้ไขทุกหมู่ | อ่านข้อมูลบัญชีตนเอง | ตรวจและอนุมัติหลังยืนยันรหัสผ่านซ้ำ |
| ผู้บริหาร (`manager`) | อ่านทุกหมู่ | อ่านข้อมูลบัญชีตนเอง | ไม่มีสิทธิ์ |
| ผู้ดูแล (`admin`) | อ่าน/เพิ่ม/แก้ไขทุกหมู่ | จัดการผ่าน RPC ตรวจสิทธิ์ | ตรวจและอนุมัติหลังยืนยันรหัสผ่านซ้ำ |

อสม. ที่ไม่ระบุหมู่ไม่มีสิทธิ์อ่านประชากร การกำหนดขอบเขตนี้เป็นระดับหมู่ ไม่ได้จำกัดรายบ้านตามชื่อ อสม. ไม่มีบทบาทใดลบประชากรผ่าน Data API ในชุดนี้

## การทำงาน

- หน้าเว็บเรียก `/api/auth/*` และ `/api/data/*` ของ Next.js ข้อมูลประชากรใช้ anon key ร่วมกับเซสชันที่เซิร์ฟเวอร์ใส่ให้ จึงยังผ่าน RLS ไม่ใช้ service-role bypass สำหรับงานประชากร
- คุกกี้ `population_session` เป็น HttpOnly, SameSite=Lax, Secure บน Production และมีอายุ 8 ชั่วโมง ฐานข้อมูลเก็บเฉพาะแฮชของโทเคนสุ่ม 256 บิต
- ทุกคำขอตรวจบัญชีที่ยังใช้งานและบทบาทปัจจุบันจากฐานข้อมูล ออกจากระบบ ระงับบัญชี เปลี่ยนรหัสผ่าน หรือแก้สิทธิ์จะยกเลิกการเข้าถึงเดิม
- เซิร์ฟเวอร์ตรวจ LINE access token กับ LINE ตรวจ channel ID และเวลาหมดอายุ แล้วอ่านโปรไฟล์จาก LINE ไม่รับ LINE user ID หรือบทบาทที่เบราว์เซอร์ส่งมาเป็นหลักฐาน
- รับรหัสผ่านเดิม SHA-1 / SHA-256 แล้วอัปเกรดเป็น bcrypt ของ SHA-256 พร้อม salt หลังเข้าสู่ระบบด้วยรหัสผ่านสำเร็จ ไม่เปลี่ยนไปเก็บเลขบัตรตรง ๆ บัญชีที่ใช้ LINE อย่างเดียวยังไม่ถูกอัปเกรดแฮชจนกว่าจะยืนยันรหัสผ่าน
- รหัสผ่านผิดจำกัด 10 ครั้งต่อชื่อบัญชีใน 15 นาที การเปลี่ยนรหัสผ่านตรวจรหัสเดิมจริง และไม่ให้ลดสิทธิ์/ระงับผู้ดูแลคนสุดท้าย
- `password_hash` และ `line_user_id` ไม่เปิดให้อ่านผ่าน anon/authenticated แม้เป็นผู้ดูแลหน้าเว็บ การแก้บัญชีใช้ RPC ที่ตรวจสิทธิ์ในฐานข้อมูล
- หน้าตรวจ HOSxP ยังต้องยืนยันรหัสผ่านซ้ำ และโทเคนอนุมัติต้องเป็นของผู้ใช้เดียวกับเซสชันเว็บ

## ติดตั้งโดยสลับเว็บและฐานข้อมูลพร้อมกัน

1. สำรองฐานข้อมูลตามกระบวนการของหน่วยงาน ตรวจว่ามี admin ที่ใช้งานได้ และตรวจ `moo` ของ อสม.
2. ตั้ง `SUPABASE_SERVICE_ROLE_KEY` เป็น **Secret ฝั่งเซิร์ฟเวอร์** บน Vercel Production ห้ามเติม `NEXT_PUBLIC_` ค่าที่ใช้ร่วมกันเดิมคือ `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `NEXT_PUBLIC_LIFF_ID` และ `NEXT_PUBLIC_LINE_CLIENT_ID` (หรือ `LINE_LOGIN_CHANNEL_ID` ฝั่งเซิร์ฟเวอร์)
3. รัน `20260910_auth_prepare.sql` เพื่อเพิ่มตารางเซสชันและ RPC ขั้นนี้ยังไม่ปิดนโยบายเก่า อย่าทดสอบล็อกอินบัญชีจริงด้วยระบบใหม่ก่อนสลับเว็บ เพราะแฮชใหม่จะไม่เข้ากับเว็บเก่า
4. ทดสอบ `npm run test:auth` และ `npm run build` แล้วเผยแพร่โค้ดชุดนี้ ต้องตั้งค่าบน Preview แยกเองหากจะใช้ Preview และอย่าใช้ Preview ที่ไม่ไว้ใจร่วมกับฐาน Production
5. เมื่อเว็บใหม่ Ready ให้รัน `20260910_auth_activate.sql` ทันที เพื่อเปิด RLS และยกเลิกนโยบายเปิดทั่วไป ทั้งชุดอยู่ใน transaction ไม่มีการลบทะเบียนประชากร
6. ตรวจ `/api/auth/session` เมื่อไม่ได้ล็อกอินต้องได้ `user:null` และ `/api/data/population` ต้องได้ 401 ล็อกอินด้วย LINE จริงและทดสอบ อสม./เจ้าหน้าที่/ผู้บริหารตามตารางสิทธิ์
7. ตรวจ Supabase API โดยไม่ส่งเซสชันต้องอ่านประชากรไม่ได้ และอ่าน `password_hash` ไม่ได้ ตรวจหน้าคัดกรอง แผนที่ และตรวจ HOSxP หลังล็อกอิน

หลังเปิด RLS ห้าม rollback ไปใช้หน้าเว็บเก่าหรือเปิดนโยบาย `true` เพื่อแก้ชั่วคราว หากมีปัญหาให้คง RLS และแก้โค้ดใหม่ หรือใช้หน้าปิดปรับปรุงระหว่างแก้ ก่อนย้อนเวอร์ชันต้องเตรียมรุ่นที่รองรับเซสชันและแฮชใหม่แล้ว

## ชุดทดสอบ

`npm run test:auth` ใช้ PostgreSQL จำลองในหน่วยความจำพร้อม pgcrypto และข้อมูลสมมติ ไม่ต่อฐานจริง ทดสอบ anonymous, ข้ามหมู่, ปลอมบทบาท/LINE, หมดอายุ, ระงับบัญชี, logout, เปลี่ยนรหัส, อัปเกรดแฮช, rate limit, ผู้ดูแลคนสุดท้าย และโทเคนตรวจ HOSxP ที่ต้องเป็นผู้ใช้เดียวกัน ส่วน API ทดสอบคุกกี้/CSRF/LINE channel/การส่งคีย์ฝั่งเซิร์ฟเวอร์ และไม่รายงานสำเร็จเมื่อแก้ไขได้ 0 แถว
